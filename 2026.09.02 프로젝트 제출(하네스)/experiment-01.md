# experiment-01 — 승인 프롬프트를 줄이면 과업이 실제로 빨라지는가

- 작성일: 2026-09-02
- 대상 하네스: Claude Code CLI 2.1.258 (Windows 10, Windows PowerShell 5.1)
- 조작한 하네스 기능: **권한 규칙(allowlist)의 범위** 하나
- 상태: **6회 실행 완료.** 사전 판정식 결과 **지지** — 단, 인과 설명은 약하다.

## 1. 관찰한 불편

> 관찰 날짜와 과업 이름은 본인 세션 기록으로 채워 넣을 것: **날짜 ____ / 과업 ____**

Windows 10 에서 Claude Code 로 Python 스크립트 과업을 맡길 때, 모델이 스스로 짠 코드를 확인하려고
`python verify.py`, `python -m unittest` 같은 명령을 돌릴 때마다 승인창이 떴다.
한 과업에서 같은 계열의 명령을 열 번 넘게 실행하는데, 그때마다 진행이 멈춘 채 내 키 입력을 기다렸다.
잠깐 자리를 비우면 돌아왔을 때 모델은 첫 번째 승인창에서 그대로 멈춰 있었다.

"도구가 불편하다"가 아니라 이렇게 적는다:
**입력** — `TASK.md 의 요구를 만족시켜라, 완료 판정은 python verify.py 가 PASS 를 내는 것이다`
**증상** — 편집 → 실행 → 확인 루프의 **실행 단계마다** 승인 대기가 삽입되어, 모델의 작업이 아니라
사람의 반응 속도가 완료 시각을 정한다.

### 이 불편이 정말 하네스 기능 때문인가 (다른 원인 목록)

실험 전에 미리 의심 목록을 적어 둔다. 뒤의 통제 조건은 이 목록에 대응한다.

| 후보 원인 | 왜 의심스러운가 | 어떻게 배제하나 |
|---|---|---|
| 모델 선택 | 모델이 느리면 승인과 무관하게 시간이 는다 | 6회 모두 같은 모델로 고정 |
| 과업 난이도 | 어려운 과업일수록 실행 횟수가 늘어난다 | 과업을 fixture 로 고정하고 같은 과업의 A/B 만 비교 |
| 저장소 상태 | 앞선 실행의 잔여물이 다음 실행을 돕거나 방해한다 | 회차마다 깨끗한 복사본에서 새 세션 |
| 네트워크 | 응답 지연이 시간을 지배할 수 있다 | 같은 날 연속 실행 + 승인 대기 시간을 분리 측정 |
| **내 요청 문장** | 문장이 넓으면 모델이 명령을 더 많이 시도한다 | 6회 모두 같은 문장을 그대로 붙여넣기 |
| 내 반응 속도 | 조건마다 내가 느리게 눌렀을 수 있다 | 3초 내 응답 규약 + 대기 시간 별도 기록 |

## 2. 가설

> **Claude Code 의 프로젝트 권한 규칙(`permissions.allow`)에 해당 과업에서 반복되는 실행 계열 명령
> (`python`, `python -m unittest` 등)을 미리 등록하면, 등록하지 않은 조건에 비해
> 같은 과업의 승인 프롬프트 횟수와 벽시계 완료 시간이 함께 줄어든다.**

**반증 조건 (이렇게 나오면 가설이 틀린 것으로 인정한다)**

- 승인 횟수는 줄었는데 **완료 시간이 줄지 않거나 오히려 늘어난 경우** → 기각.
  (승인 대기가 총 시간의 지배 요인이 아니었다는 뜻이 된다.)
- 승인 횟수 자체가 절반 아래로 안 내려간 경우 → 조작이 걸리지 않았거나 규칙 범위가 잘못 잡힌 것.
- 조건 B 에서 과업 검증(`verify.py` PASS)에 실패한 과업이 하나라도 있는 경우 → 부작용으로 기각.

가설은 "편해진다"가 아니라 **수치로 반증 가능한 문장**이어야 한다. 그래서 "승인 횟수"와 "완료 시간"을
동시에 걸었다. 하나만 걸면 승인만 줄고 시간은 그대로인 결과를 "지지"라고 우겨 버릴 수 있다.

## 3. 배경 근거

전체 카드는 [`evidence/evidence-cards.md`](evidence/evidence-cards.md). 요약하면:

| 카드 | 등급 | 내용 | 이 카드가 **검증하지 않은 것** |
|---|---|---|---|
| C-01 | `[공식 문서]` | `permissions.allow` 규칙에 매칭되는 도구 호출은 묻지 않고 실행된다 | **시간이 줄어드는지는 말하지 않는다.** 동작 규정일 뿐 성능 주장이 아니다 |
| C-02 | `[공식 문서]` | `acceptEdits` 모드는 편집 승인을 자동 수락한다 | 실행 후 확인됨: 이 모드에서 Bash 승인은 유지된다. 단 `ls`/`cat`/`echo` 는 allowlist 와 무관하게 통과한다 |
| C-03 | `[벤더]` | 제작사가 안전한 명령을 allowlist 에 넣으라고 권장 | **벤더 자체 보고이며 독립 비교가 아니다.** 대조군·표본·측정법이 공개되지 않았다 |
| C-04 | `[학술]` | 작업 중단이 재개 비용을 만든다 | 🔴 **원문 미확인.** 확인 전까지 수치 근거로 쓰지 않는다 |

**등급을 숨기지 않기 위해 명시한다.** 이 가설을 뒷받침하는 것은 `[공식 문서]` 의 *동작* 규정과
`[벤더]` 의 *권장*뿐이고, "얼마나 빨라지는가"에 대한 수치 근거는 **어느 카드에도 없다.**
그 빈칸이 이 실험이 존재하는 이유다.

## 4. 실험 설계

| 구분 | 내용 |
|---|---|
| **고정** | Claude Code 같은 버전·같은 모델 / 같은 fixture 3개 / 같은 요청 문장 / 6회 모두 새 세션·새 폴더 / 6회 모두 `--permission-mode acceptEdits` / 전역 설정 무변경 / 같은 날 연속 실행 |
| **조작** | 프로젝트 `.claude/settings.json` 의 `permissions.allow` **한 가지만**<br>· **조건 A(대조)**: `allow: []` — 실행 명령마다 승인창<br>· **조건 B(처치)**: `Bash(python:*)` 등 실행 계열 8개 사전 등록 |
| **측정** | ① 승인 프롬프트 횟수 ② 벽시계 완료 시간(초) ③ 승인 대기 시간 합(초) ④ 순수 실행 시간(②−③) ⑤ `verify.py` 시도 횟수 ⑥ 검증 통과 여부 ⑦ 비용/토큰(`/cost`) |
| **사전 판정식** | 3개 과업 중 **2개 이상**에서 `B 승인 ≤ A 승인 × 0.5` **이면서** `B 시간 ≤ A 시간 × 0.8` 이면 **지지**.<br>미달이거나, 조건 B 에 검증 실패가 하나라도 있거나, B 총비용 > A 총비용 × 1.5 이면 **기각**. 보류는 없다. |

판정식은 [`scripts/tally.py`](scripts/tally.py) 맨 위 상수에 **코드로 박아** 두었다.
결과를 본 뒤 기준을 손보는 일을 막으려는 장치다.

### 왜 편집 승인은 조작하지 않았나

`acceptEdits` 를 **양 조건 모두에** 걸어 편집 승인을 0으로 만들었다.
allowlist 로 편집까지 함께 열면 조작 항목이 "실행 승인 + 편집 승인" 둘이 되어,
시간이 줄어도 무엇 때문인지 말할 수 없다. 조작은 **Bash 실행 승인 하나**로 좁혔다.

### 고정 과업 (fixture) 3개

입력 파일은 미리 만들어 두었고 실험 중 내용을 바꾸지 않는다. 조건 차이가 과업 난이도 탓이 아니라
권한 규칙 탓이라고 말하려면 이 고정이 필요하다.

1. [`task1 parse-log`](fixtures/task1-parse-log/) — `sample.log` 에서 `ERROR` 줄만 골라 코드별 건수 표를 내는 `parse.py` 작성.
   `INFO`/`WARN` 본문에 섞인 `ERROR`·`code=` 가 함정이라 한 번에 맞히기 어렵다 → 실행·수정 루프가 반복된다.
2. [`task2 refactor-util`](fixtures/task2-refactor-util/) — `util.py` 함수 3개에 타입 힌트·독스트링 추가. 동작은 유지.
3. [`task3 fix-failing`](fixtures/task3-fix-failing/) — `test_me.py` 의 실패 2건이 통과하도록 `shipping.py` 수정.
   테스트 파일은 sha256 으로 고정되어 수정하면 채점기가 잡는다.

세 과업 모두 채점기 `verify.py` 가 `PASS`/`FAIL` 을 객관적으로 낸다.
**외부 패키지를 쓰지 않는다.** 이 PC 에 pytest 가 없어서, 만약 설치가 필요한 과업이었다면
"설치 명령 승인"이라는 교란 요인이 조건마다 다르게 끼어들었을 것이다. 표준 라이브러리만 쓰도록 짠 이유다.

### 예상 반론과 통제 조건

| # | 예상 반론 | 이 반론과 가설을 구분하는 통제 |
|---|---|---|
| R-1 | "두 번째 실행이라 빨라진 것뿐이다" | 과업별로 조건 순서를 교차 배치(1:A 2:B 3:A 4:B 5:A 6:B). 매회 깨끗한 복사본 + 새 세션이라 모델에는 기억이 남지 않는다 |
| R-2 | "승인이 아니라 모델·네트워크 지연이 시간을 지배했다" | 승인 대기 시간을 따로 재서 **순수 실행 시간**(총−대기)을 함께 본다. 대기를 빼도 B 가 빨랐다면 그건 가설로 설명이 안 된다 → 그 자체가 기각 신호 |
| R-3 | "규칙이 넓으면 모델이 더 과감해져서 명령·토큰이 늘 것이다" | 시도 횟수와 비용을 측정하고, B 비용이 A 의 1.5배를 넘으면 부작용으로 기각 |
| R-4 | "내가 조건마다 다른 속도로 승인을 눌렀다" | 3초 내 응답 규약, `always allow` 금지. 어기면 그 run 은 폐기 후 재실행 |
| R-5 | "조건 A 인데 실은 전역 설정이 이미 허용하고 있었다" | 사전 점검 P-3/P-4 에서 승인창이 실제로 뜨는지 리허설로 확인 |

R-1 은 완전히 배제되지 않는다. 과업이 3개라 A 선행 2회 / B 선행 1회로 **순서가 완전히 균형 잡히지 않는다.**
남은 순서 효과는 잔여 교란으로 인정하고, 2회차에서 순서를 뒤집어 확인한다.

### 자동 실행을 시도했다가 버린 기록

6회를 사람이 앉아 누르는 대신 헤드리스(`claude -p`)로 자동 실행하려 했고, 승인 대기를 3초 고정
응답 훅(`protocol/approve_hook.py`)으로 재현했다. **작동은 했지만 채택하지 않았다.**

리허설(`runs/r9_rehearsal_task1_A`)에서 `cd "<작업폴더>" && python verify.py` 형태의 호출이
**훅이 발동하기도 전에 거절**됐고, 에이전트는 `cd` 접두사를 뺀 형태로 재시도해 통과했다.
이 거절-재시도는 대화형 실행에는 없다. 그리고 조건 B 는 allowlist 가 `python:*` 을 덮어
그 경로를 아예 타지 않으므로, **조건 A 에만 헤드리스 고유의 마찰이 추가된다.**
그 상태로 6회를 돌리면 A 가 느린 이유가 승인 대기인지 거절-재시도인지 구분할 수 없다.

따라서 이 실험은 대화형 실행이 아니면 성립하지 않는다. 훅과 러너는 저장소에 남겨 두었다
(다음 실험 4번 항목의 재료다).

| task1 | B | 0 | 20.9 | — | 20.9 | 1 | yes | 638,378 |
| task2 | A | 1 | 23.5 | 2.0 | 21.5 | 1 | yes | 363,048 |

| task3 | A | 1 | 25.6 | 3.6 | 22.0 | 1 | yes | 470,616 |

`승인 호출 지연 합` = 승인이 필요했던 Bash 호출들의 지연 합. 승인 대기와 명령 실행 시간이
섞여 있으므로 **승인 대기의 상한**으로만 읽는다. 조건 B 는 승인 호출이 없어 빈칸이다.

승인 횟수는 규칙을 명령 원문에 대입해 **유도한** 값이다. 1회차에서 사람이 실제로 센 횟수(1회)와
유도값(1회)이 일치함을 확인한 뒤 나머지 회차에 적용했다.

## 8. 원인 검토 — 불편의 진짜 원인이 이 하네스 기능이었나

**R-2 통제가 발동했다. 그리고 가설에 불리한 방향이다.**

설계 때 이렇게 적어 두었다: *"대기를 빼도 B 가 빨랐다면 그건 가설로 설명이 안 된다 → 그 자체가 기각 신호."*
승인 호출 지연을 뺀 "나머지 시간"을 보면:

| 과업 | A 나머지 | B 나머지 | 차이 |
|---|---|---|---|
| task1 | 19.4 | 20.9 | B 가 **1.5초 느림** |
| task2 | 21.5 | 17.1 | B 가 4.4초 빠름 |
| task3 | 22.0 | 19.9 | B 가 2.1초 빠름 |

방향이 일관되지 않고, 평균으로도 B 의 나머지 시간이 A 보다 1.7초 빠르다.
**승인 대기와 무관한 부분에서 이미 1.7초가 벌어져 있다는 뜻이다.**

완료 시간 차이(A−B)는 task1 5.3초, task2 6.4초, task3 5.7초였다. 그런데 조건 A 의 승인 호출
지연 합은 6.8초, 2.0초, 3.6초로 편차가 크고, task2 는 **승인 지연 2.0초로 6.4초 차이를 설명할 수 없다.**

즉 20초대 과업에서 회차 간 변동폭이 조작 효과와 같은 크기다. 사전 판정식은 통과했지만,
**"승인 프롬프트를 없앤 것이 시간을 줄였다"는 인과 설명은 이 데이터로 뒷받침되지 않는다.**

- **관찰된 원인 설명의 강도**: 약하다. 승인 횟수에 대한 조작 효과는 명확하지만(1 → 0, 3/3 과업),
  완료 시간에 대해서는 조작 효과와 잡음을 분리하지 못했다.
- **원인 설명을 약하게 만든 것**:
  1. 과업당 표본 1회. 반복이 없어 변동폭을 추정할 수 없다.
  2. 과업이 20초대로 짧다. 승인 1회당 수 초가 전체의 20~25% 를 차지해 비율은 커 보이지만,
     같은 크기의 잡음에 묻힌다.
  3. 조건 A 의 승인 횟수가 **과업당 1회뿐**이었다. 설계 때는 "한 과업에서 열 번 넘게"를 가정했는데,
     실제 에이전트는 `verify.py` 를 한 번만 돌리고 끝냈다. 조작할 대상 자체가 예상보다 작았다.
  4. `ls`/`cat`/`echo` 가 allowlist 와 무관하게 통과하므로, 조건 A 조차 "모든 명령이 막힌 상태"가
     아니었다. 두 조건의 실제 차이는 python 계열 호출 하나뿐이다.
- **다음 실험에서 고정하거나 바꿀 조건**: 반복 횟수(과업당 최소 5회), 승인이 여러 번 발생하는
  더 긴 과업, 그리고 시간이 아니라 **승인 횟수와 대기 시간 합**을 1차 지표로 삼는 것.

한 가지는 분명하게 말할 수 있다. **조작은 승인 횟수를 확실히 줄였다**(3/3 과업에서 1 → 0).
불확실한 것은 그것이 완료 시간으로 이어지는지다. 그리고 내가 원래 겪은 불편은 "완료가 느리다"가
아니라 "자리를 비우면 멈춰 있다"였는데, 그 불편은 **승인 횟수가 0이 되면 정의상 사라진다.**
시간 단축을 증명하지 못해도 불편 자체는 해소된다는 뜻이고, 그렇다면 애초에 가설에 완료 시간을
건 것이 과했을 수 있다.

## 9. 다음 실험 계획

1. **반복을 붙인다.** 같은 설계로 과업당 조건별 5회씩, 총 30회. 회차 간 변동폭을 먼저 추정하고
   그 다음에 효과 크기를 본다. 지금 데이터로는 20초대 과업의 표준편차조차 모른다.
2. **승인이 여러 번 발생하는 과업으로 바꾼다.** 지금 과업은 승인이 1회뿐이라 조작 대상이 너무 작았다.
   실행-수정 루프가 5회 이상 돌아야 하는 과업(예: 실패 테스트 5건, 의존성 있는 리팩터링)으로 교체한다.
3. **대기 길이를 직접 조작한다.** 승인 횟수는 고정하고 사람의 응답을 3초 / 30초로 나눠 실행한다.
   시간 차이가 승인 **횟수**에서 오는지 **대기 길이**에서 오는지 분리된다.
4. **헤드리스 거절 경로를 따로 조사한다.** `cd "<경로>" && cmd` 가 훅보다 먼저 거절되는 이유를
   확인한다. 이것이 해결되면 자동 반복 실행이 가능해져 1번 항목의 30회가 현실적이 된다.
5. **`[학술]` 카드 C-04 의 원문을 확인한다.** 확인 전까지 이 보고서는 학술 근거 없이 서 있다.

  이 명령들은 allowlist 가 완전히 비어 있어도 하네스가 자체적으로 통과시킨다.
  allowlist 를 넓게 적어 두었어도 실제로 작동한 것은 일부였다.

- 승인 횟수는 규칙으로 **유도한** 값이다. 1회차에서만 사람이 센 값과 대조했다.

- 완료 시간 단축이 실재하는지. 지지 판정이 나왔지만 마진이 잡음 크기다.

- `acceptEdits` 에서 하네스가 자체 통과시키는 명령의 전체 목록. `ls`/`cat`/`echo` 만 확인했다.

- `[학술]` 카드 C-04 의 원문. 미확인 상태이며 수치 근거로 쓰지 않았다.
